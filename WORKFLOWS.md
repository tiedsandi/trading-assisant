# AI Development Workflow

This document defines the collaboration workflow between the project owner,
ChatGPT as planner/reviewer, and local coding agents.

## Roles

### Project Owner

- Defines product intent and makes final decisions.
- Provides implementation instructions to coding agents.
- Reviews the product outcome when necessary.
- Commits and pushes approved changes.

### ChatGPT

Acts as planner and reviewer.

Responsibilities:

- Understand product context before proposing implementation.
- Clarify feature requirements before implementation.
- Define goal, user flow, functional requirements, data, scope, and acceptance criteria.
- Avoid generating implementation instructions while material requirements remain ambiguous.
- Produce `instruksi.md` content for coding agents.
- Review coding-agent Handoff Reports against the original instruction.
- Request targeted diffs/files when deeper technical review is necessary.
- Decide whether work is ready to commit or requires revision.

### Coding Agent

Codex, Claude Code, Gemini, or another repository-aware coding agent.

Responsibilities:

- Follow `AGENTS.md`.
- Understand the complete instruction before editing.
- Inspect relevant existing code and configuration.
- Treat the repository as the source of truth.
- Plan before implementation.
- Implement only the requested scope.
- Verify changes.
- Update project context when required.
- Produce the required Handoff Report.
- Do not commit or push unless explicitly requested.

---

## Development Flow

```text
Design
→ Instruction
→ Understand
→ Inspect
→ Plan
→ Implement
→ Verify
→ Document
→ Handoff
→ Review
→ Commit
→ Next Task
```

Do not start implementation while material product requirements are ambiguous.

The normal workflow is:

1. Project Owner and ChatGPT design the feature/task.
2. ChatGPT produces an `instruksi.md`.
3. Project Owner copies the instruction to a coding agent.
4. Coding agent understands, inspects, plans, and implements.
5. Coding agent verifies the implementation.
6. Coding agent updates project context when required.
7. Coding agent returns a Handoff Report.
8. Project Owner sends the Handoff Report to ChatGPT.
9. ChatGPT reviews the result.
10. Approved work may be committed and pushed.
11. If necessary, ChatGPT produces a focused revision instruction.

---

## Feature Design

Before implementation, define when applicable:

- Goal
- User flow
- Functional requirements
- Data to store
- API behavior
- UI behavior
- Security requirements
- Constraints
- Out of scope
- Acceptance criteria

Do not force sections that are irrelevant to the task.

If a material requirement is unclear and different interpretations could
significantly change the implementation, clarify it before generating the
final implementation instruction.

---

## Implementation Instruction (`instruksi.md`)

`instruksi.md` is the name used in this workflow for a temporary implementation
prompt generated by ChatGPT and copied by the Project Owner to a coding agent.

It is NOT a repository file and should not be committed.

An implementation instruction should contain the following sections when
applicable:

1. Execution Protocol
2. Task
3. Context
4. Goal
5. User Flow
6. Functional Requirements
7. Frontend Requirements
8. Backend Requirements
9. Data Requirements
10. Security Requirements
11. Technical Constraints
12. Out of Scope
13. Acceptance Criteria
14. Verification
15. Documentation Update
16. Required Handoff Report

Sections that do not apply to a particular task may be omitted rather than
filled with unnecessary content.

---

## Execution Protocol

Every `instruksi.md` must instruct the coding agent to follow this protocol
before implementation:

1. Read the entire instruction before making changes.
2. Read `AGENTS.md`, `docs/ai/CURRENT.md`, and `docs/ai/CONVENTIONS.md`.
3. Inspect repository code and configuration relevant to the task.
4. Treat the repository as the source of truth.
5. Understand the goal, scope, constraints, and acceptance criteria.
6. Create an implementation plan before editing files.

The coding agent must not blindly implement assumptions from the instruction.

If the instruction conflicts with repository reality:

- STOP.
- Explain the conflict.
- Do not work around the conflict by silently changing the requested scope.

If a material ambiguity could significantly change architecture, behavior,
security, data design, or scope:

- STOP.
- Ask for clarification before implementation.

If the task is sufficiently clear and the repository supports the plan:

- Proceed with implementation without waiting for unnecessary approval.

During implementation:

- Stay within the requested scope.
- Avoid unrelated refactors.
- Preserve existing user changes.
- Follow existing code conventions.
- Do not weaken or remove tests merely to make checks pass.
- Do not introduce unnecessary dependencies, abstractions, or architecture.
- Report any necessary deviation from the instruction.

After implementation:

1. Run relevant tests and checks defined by the task and `AGENTS.md`.
2. Fix failures caused by the implementation.
3. Update `docs/ai/CURRENT.md` when project state changes.
4. Append a concise entry to `docs/ai/LOG.md` for meaningful changes,
   decisions, or verification.
5. Do not commit or push unless explicitly requested.
6. Produce the required Handoff Report.

## Handoff Report

Every implementation task must end with the following report.

```md
# Handoff Report

## 1. Status

DONE / PARTIAL / BLOCKED

## 2. What Was Implemented

- Summarize the completed behavior.
- Keep this focused on the requested task.

## 3. Files Changed

- `path/to/file` — short description of the change.

## 4. Database Changes

Describe migrations, tables, columns, constraints, or indexes.

Write `None` when there are no database changes.

## 5. API Changes

List endpoints or API behavior that was added or changed.

Write `None` when there are no API changes.

## 6. Verification

List every relevant check using:

- `<check>`: PASS
- `<check>`: FAIL
- `<check>`: NOT RUN

For FAIL, include the important failure details.
For NOT RUN, explain why when relevant.

Never report a check as PASS unless it was actually executed successfully.

## 7. Acceptance Criteria

Repeat the acceptance criteria from the instruction:

- [x] Satisfied criterion
- [ ] Unsatisfied criterion

Explain every unchecked criterion.

## 8. Decisions / Assumptions

List implementation decisions or assumptions that were not explicitly
specified by the instruction.

Write `None` when there are none.

## 9. Issues / Remaining Work

List known issues, blockers, or remaining work.

Write `None` when the requested scope is complete.

## 10. Git

- Commit: CREATED / NOT CREATED
- Push: PERFORMED / NOT PERFORMED

Include commit information only when explicitly requested.

## 11. Suggested Review

List files or areas that deserve manual review, especially:

- core business logic
- authentication/security
- database migrations
- destructive changes
- important architectural decisions

Write `None` when no targeted review is necessary.
```

The Handoff Report is the default artifact returned to ChatGPT for review.

Do not send the entire codebase by default.

ChatGPT may request specific files or diffs after reviewing the report.

---

## Review Policy

ChatGPT reviews the Handoff Report against:

1. The original `instruksi.md`.
2. The acceptance criteria.
3. Reported verification results.
4. Decisions and assumptions made during implementation.
5. Remaining issues.

There are three possible review outcomes.

### APPROVED

The implementation appears to satisfy the requested scope and acceptance
criteria.

The Project Owner may commit and push the changes.

### REVIEW REQUIRED

The report is not sufficient to safely approve the implementation.

ChatGPT requests only the relevant files, diffs, test output, or other
evidence needed for deeper review.

Do not request the entire codebase by default.

### REVISION REQUIRED

The implementation does not satisfy the instruction or acceptance criteria.

ChatGPT produces a focused revision instruction for the coding agent.

The revision should address the identified problems without unnecessarily
reimplementing completed work.

---

## Git Policy

Coding agents do not commit or push unless explicitly requested.

Default flow:

```text
Implementation
→ Handoff
→ Review
→ Approval
→ Project Owner commits
→ Push
```

A clean Handoff Report does not automatically authorize a commit.

The Project Owner makes the final decision.
